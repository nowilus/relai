1

Streszczenie

RelAI to plugin Claude Code, który sprawia, że każdy projekt — aplikacja, agent głosowy, flow N8N czy zestaw promptów — dokumentuje się sam, na bieżąco, według jednego sprawdzonego stylu. Użytkownik instaluje plugin dwiema komendami i pisze pierwszy prompt; RelAI zakłada strukturę, prowadzi dziennik, pilnuje planów, backupów i sekretów, a projekt w każdej chwili jest gotowy do przekazania innej osobie.

Plan powstał na bazie analizy FAKT kilkunastu projektów z 5 miesięcy pracy (4 ery ewolucji stylu) oraz wywiadu architektonicznego: FAKT 24 rundy pytań, ~90 zamrożonych decyzji (rejestr: DECYZJE.md, D-01…D-84).

Budowa: FAKT 10 etapów, MVP-first (po E2 rdzeń jest używalny). Łączny nakład: SZACUNEK 16–24 sesje robocze modelu wykonawczego, przy Twoim tempie ok. 2–4 tygodnie kalendarzowe.

2

Wizja i cele

Zasada naczelna: zero konfiguracji, zero pamiętania składni, zero martwych dokumentów. RelAI pyta o preferencję raz, w naturalnym momencie, zapisuje ją i respektuje na zawsze.

  • Powtarzalność — każdy nowy projekt zaczyna się identycznie: ta sama struktura, te same rytuały, ten sam standard dokumentów.
  • Aktualność — STATE opisuje stan aplikacji „na dziś" (aktualizacja to część definicji ukończenia zadania, nie osobny obowiązek). Na pytanie szefa „co robi ta funkcja?" odpowiada dokument, nie pamięć developera.
  • Przekazywalność — komenda przekazania + wycieczka dla nowej osoby; urlop przestaje być ryzykiem projektu.
  • Uniwersalność — jeden rdzeń + profile: aplikacje (web/mobile/backend), agenci głosowi ElevenLabs, flow N8N, projekty czysto promptowe.
  • Bezpieczeństwo — sekrety blokowane przed zapisem do repo, backupy z automatu je wykluczają, konfiguracje produkcyjne agentów snapshotowane przed każdą zmianą.

Odbiorcy: najpierw Ty (idealnie skrojony pod Twój styl), potem współpracownicy w firmie (instalacja bez konfiguracji), docelowo publiczny open-source.

4

Warianty architektoniczne — rozważone i rozstrzygnięte

4.1 Forma dystrybucji

Plugin Claude Code WYBRANY

Instalacja 2 komendy, zero kopiowania repo i odpinania gita, aktualizacje docierają globalnie do wszystkich użytkowników, a pliki projektów pozostają nietknięte. Rozwiązuje główny grzech vibe-forge (zamrożone snapshoty bez ścieżki aktualizacji).

Repo-szablon do kopiowania ODRZUCONY

Powód: tarcie przy starcie (klon → odpinanie gita → własne repo), brak dystrybucji aktualizacji — dokładnie ten model zabił vibe-forge. README szablonu myli się z README projektu użytkownika.

Hybryda plugin + repo-startowe ODRZUCONY

Powód: dwa artefakty do utrzymania w zgodzie od pierwszego dnia; wartość dodana minimalna, skoro plugin sam zakłada strukturę.

4.2 Generacja dokumentów projektowych

Szablony jako specyfikacje dla LLM WYBRANY

Szablon opisuje strukturę, zasady i przykłady — dokument generuje LLM w języku projektu. Jeden kanoniczny zestaw obsługuje PL/EN/dowolny język już w v1, bez pracy tłumaczeniowej. Naturalnie dopasowuje treść do kontekstu projektu.

Statyczne pliki kopiowane per język ODRZUCONY

Powód: każda zmiana szablonu × liczba języków; nowe języki niemożliwe bez wydania pluginu; treść szablonowa zamiast dopasowanej (syndrom ~120 placeholderów vibe-forge bez silnika substytucji).

4.3 Technologia hooków

Node.js — jeden plik na hook WYBRANY

Cross-platform bez dublowania (koniec z parami .ps1+.sh z ryzykiem rozjazdu logiki), Node jest zawsze dostępny w środowisku Claude Code, wzorzec sprawdzony w istniejących pluginach.

Pary .ps1 + .sh ODRZUCONY

Powód: każda poprawka robiona dwa razy; historia Twoich projektów pokazuje rozjazdy między wersjami platformowymi.

PowerShell Core ODRZUCONY

Powód: wymaga instalacji pwsh na macOS/Linux — nieakceptowalne przy ambicji publicznej dystrybucji.

4.4 Egzekwowanie zasad w codziennej pracy

Warstwa potrójna: CLAUDE.md projektu + skille auto-wyzwalane + hooki WYBRANY

„Przygotuj plan" w zwykłym prompcie wystarcza — reguły siedzą w kontekście (CLAUDE.md), skille dołączają wiedzę proceduralną, hooki pilnują twardych granic. Komendy tylko dla operacji rzadkich. Realizuje wymóg „zero pamiętania składni".

Wszystko przez jawne komendy ODRZUCONY

Powód: obowiązek pamiętania wywołań przy każdej wiadomości — wprost odrzucony w wywiadzie.

Rejestr decyzji (skrót)

Pełny rejestr: DECYZJE.md — FAKT 45 wpisów D-01…D-84 w 8 grupach. Najważniejsze kotwice:

  • Tożsamość: RelAI, plugin samowystarczalny, komendy EN, repo prywatne → publiczne (D-01…D-06).
  • Dokumenty: triada + STATE + USTAWIENIA + KOMENDY; CAPS_SNAKE PL bez dat; wszystko w docs/ (D-10…D-19).
  • Interakcja: zgoda + 3 pytania na starcie; „zapytaj raz, zapisz, respektuj"; tryb gościa przy odmowie (D-20…D-27).
  • Plany: folder-per-plan; PLAN/MINIPLAN; zamrożenie + aneksy; prompty etapowe lazy z rytuałem „Na koniec" (D-30…D-38).
  • Bezpieczeństwo: blokada sekretów, backup bez sekretów, docs aktualne = definicja ukończenia (D-40…D-45).
  • Profile: app / agent-voice / flow / prompty; snapshoty obowiązkowe dla configów produkcyjnych (D-50…D-53).
  • Szablony: specyfikacje dla LLM; konkurs designu 5 propozycji; lokalne nadpisania (D-60…D-63).
  • Adopcja/aktualizacje: tylko na żądanie, backup+raport+recovery; /relai-update z diffem (D-70…D-72).

E1Fundament repo pluginu + inicjalizacja projektu1–2 sesje

Przypadki brzegowe — rozstrzygnięte

  • Sesja przerwana w połowie rytuału „Na koniec" → session-context wykrywa lukę (etap zamknięty, brak promptu N+1) i dogenerowuje na starcie (D-34).
  • Projekt bez gita → dozwolony z ostrzeżeniem; zakaz zagnieżdżonych repo bezwzględny (D-53); backupy i snapshoty przejmują rolę siatki.
  • Projekt w języku innym niż PL/EN → generacja LLM ze specyfikacji obsługuje dowolny język (D-60); nazwy plików podążają za językiem.
  • Istniejący CLAUDE.md przy adopcji → scalanie z zachowaniem: backup + sekcja „Zasady odziedziczone" + konflikty rozstrzygane pytaniami (D-71).
  • Użytkownik ma ECC / superpowers / caveman → RelAI współistnieje, niczego nie dubluje ani nie wymaga (D-04).
  • Nieznany autor otwiera projekt → propozycja tour; odmowa szanowana (D-27).
  • Zmiana produkcyjna configu agenta bez snapshotu → profil agent/flow traktuje snapshot jako bramkę: najpierw snapshot, potem zmiana (D-52).
  • Duże pliki binarne (screenshoty QA, PDF-y) → wyłącznie docs/zasoby/; root i docs/ główne wolne od binariów.
  • Dokument przestaje być aktualny → natychmiastowa adnotacja „NIEAKTUALNE (zastąpione przez, kiedy, powód)" + przeniesienie do archiwum (D-18); nigdy ciche kasowanie.
